# 周末出逃：真实用户测试脚本

状态：测试材料已准备，尚未开展学生访谈或实际出游测试。功能测试与 AI 模拟不能替代真实用户证据。

## 参与者与方法

邀请 5—8 名自愿参与的在校学生，涵盖独自出门、与熟人同行，以及曾放弃过周末出游的人。先问最近一次真实经历，再做任务，不提前解释推荐理由。记录可用匿名编号，避免收集学号、身份证或私人住址。

体验入口：https://zhanghengrui2026-stack.github.io/Weekend-Trip/

## 开场与经历访谈（5 分钟）

说明是在测试产品，不是测试参与者；任何时候可以退出。

1. 最近一次周末想出去玩，最后去了哪里？若没有出门，停在哪一步？
2. 用过哪些工具，花了多久决定？预算和实际开销有什么差异？
3. 跟谁一起？时间、地点和费用如何确定？
4. 有没有开放时间、预约、交通或天气信息导致计划变化？

## 任务 A：选定方案

请安排下个周末与一位朋友在徐汇玩半天，整趟人均不超过 100 元。按自己的实际交通情况填写预留，选定一份方案，并说明几点返回、哪些费用包含、哪些信息还未确认。

从开始操作计时到明确选定方案。观察用户是否发现费用可修改、时间包含往返、场馆资料不等于当天开放确认。不要代替用户点击或告诉他该选什么。

## 任务 B：变动与分享

假设当天有雨，检查当前路线是否适合，并尝试室内方案。把出发卡分享给朋友：朋友应能看到相同日期、地点、费用、来源与待确认事项。

再尝试把日期改到周一，或者把单程交通改到 90 分钟，看是否理解不可用原因。测试中的不合适条件不意味着现场无法出行；具体以官方开放通知与导航为准。

## 任务 C：行前确认

打开来源查看当天开放或预约信息；不要真的下单。按实际核对结果勾选，观察是否明白个人核对不等于预约成功或其他成员确认。

## 如何解读

保留失败和取消样本；记录原话时先获得参与者同意。小样本能发现问题，不能包装成整个大学生群体的比例。实际出发率必须有后续反馈，不能用生成、分享或打卡按钮点击代替。费用误差应把必要支出与自选购物分开。

当前版本没有收集真实多人确认、实时天气或导航数据；资料来源与未知字段已在界面标注。真实测试前应再次确认场馆当天开放和可用预约。
